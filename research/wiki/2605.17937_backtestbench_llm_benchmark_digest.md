## 2. Summary

1. **Motivation.** Quantitative backtesting — replaying trading logic on historical data to assess strategy robustness — is essential to quantitative investing but remains a high-barrier, interdisciplinary workflow requiring precise factor construction, accurate data queries, and error-free code. The paper argues that **Large Language Models (LLMs)**, with their code generation, agentic planning, and tool-use abilities, could automate this pipeline, but the field lacks a large-scale benchmark to measure whether they actually can.

2. **Core contribution.** The paper introduces **BacktestBench**, described as the **first large-scale benchmark for automated quantitative backtesting**, built from over **6 million real market records** (6,549,254 cleaned records covering 5,401 listed companies over 1,395 trading days from the Shanghai, Shenzhen, and Beijing Stock Exchanges, Jan 2020–Sep 2025). It comprises **18,246 annotated question–answer pairs** split into training (10,215), validation (4,195), and test (3,836) sets, across four task categories.

3. **Core concepts and task design.** The benchmark formalizes four related concepts — **factor** (deterministic numeric variable from market data), **signal** (Boolean rule on factors), **strategy** (composition of buy/sell signals into a trading policy), and **KPI** (evaluation metric) — and defines **43 factors** (Risk, Quality, Momentum, Technical categories) and **7 KPIs** (Return Ratio, Maximum Drawdown, Volatility, Annual Sharpe Ratio, Win Rate, Profit/Loss Ratio, Calmar Ratio). These are encapsulated into **80 atomic strategy functions** (41 sell-side, 39 buy-side), forming a combinatorial search space of **92,170 buy strategies and 112,791 sell strategies**. Four task families are constructed: **Metrics Calculation** (10,244 samples), **Ticker Selection** (3,455), **Parameter Confirmation** (2,548), and **Strategy Selection** (1,999).

4. **Dataset construction pipeline.** A standardized backtesting protocol (long-only, strictly alternating buy/sell, buy at open/sell at close, round-lot ≥100 shares, zero transaction costs, 252-trading-day annualization, daily risk-free rate 0.0001) is implemented and validated via **double-blind cross-verification** by two engineers. Natural-language strategy descriptions are generated via a **"code-to-text" reverse-engineering paradigm** using five open-source LLMs (**Kimi-K2-Thinking, MiniMax-M2.1, GLM-4.7, GPT-OSS-120B, Qwen3-235B-A22B-Thinking-2507**) deployed on 72 NVIDIA A800-SXM4-80GB GPUs, issuing **825,075 LLM calls** over 33,003 strategy programs. A strict peer-review filter requires unanimous agreement (8 positive votes across 4 auditor models on code fidelity and strategy validity) before a description is retained, yielding the final 18,246-sample corpus. **Human validation** on 200 sampled instances found a 97.5% completeness pass rate and 98.5% code-correctness consistency; a separate hand-crafted 70-strategy expert set was built to check realism.

5. **Proposed baseline: AutoBacktest.** The paper proposes **AutoBacktest**, a **multi-agent framework** (built with **LangGraph** using a **ReAct** architecture) that mimics a human quant researcher's workflow via three specialized agents: the **Summarizer** (extracts factor/KPI keywords via an LLM and matches them to standardized indicator names using **BM25** retrieval), the **Retriever** (maps indicators to compact "Short Codes" and generates/validates SQL against a **PostgreSQL** database), and the **Coder** (uses a Python REPL tool to write and execute backtesting code and extract the final answer, capped at 25 tool-call iterations).

6. **Experimental setup.** 23 mainstream LLMs were evaluated — open-source (Qwen3 family 4B–235B A22B, Ministral 3 8B/14B, Kimi K2-Thinking and Linear 48B, GLM 4.7 and Flash, GPT-OSS 120B/20B, MiniMax-M2.1, Seed OSS 36B, Mimo V2 Flash, DeepSeek V3.2) and closed-source (**Gemini 3 Pro, Qwen3 Max, Qwen3 Coder Plus, Seed 1.8**). Evaluation used Accuracy/Precision/Recall/F1 for indicator retrieval, Executable Rate (ECR) and Execution Accuracy (EA) for SQL generation, and end-to-end accuracy per task category, with metrics-calculation answers required to be within 10⁻³ absolute error of ground truth. Temperature was fixed at 0.6 across all models.

7. **Main results — closed-source dominance.** **Gemini 3 Pro** achieved the top **Overall Accuracy (OA) of 67.41%** and led Metrics Calculation at **51.67%**. The best open-source model, **GLM 4.7**, reached only **56.83% OA** and **39.13% MC**, trailing Gemini 3 Pro by **10.58 points OA and 12.54 points MC**, indicating a persistent open-source gap in complex financial logic.

8. **Scaling and Chain-of-Thought effects.** Within the Qwen3 family, shrinking from 235B to 4B parameters caused Metrics Calculation accuracy to **collapse from 34.71% to 1.77%**, while Indicator Retrieval F1 only dropped from 94.18% to 88.48%, showing that logical/mathematical reasoning is far more scale-sensitive than retrieval. Non-CoT models revealed a **"decoupling" of syntax and logic**: **Kimi Linear 48B** had a 99.22% Execution Correctness Rate but only 0.19% MC accuracy and 48.46% EA; **Seed OSS 36B** had 87.96% EA but only 11.34% OA — demonstrating that syntactically valid, executable code can still be logically wrong, and that CoT reasoning is essential for correct quantitative logic.

9. **KPI-level and ablation findings.** Complex statistical KPIs (**Volatility, Sharpe Ratio**) were "disaster zones" across all models compared to simpler ones (Win Rate, Maximum Drawdown); Gemini 3 Pro's edge was concentrated in these hardest indicators. Case studies identified root causes such as missing "Day 0" capital anchoring truncating return series, misimplemented Mean Absolute Deviation in CCI, and missing end-of-window boundary constraints causing invalid same-day trades. Ablations showed the **Short Code mechanism** (compact formula identifiers like `DELAY(HIGH,1)-DELAY(EMA(CLOSE,13),1)`) substantially boosts SQL Execution Accuracy (e.g., MiniMax M2.1 and GPT-OSS-20B gained over 20 points), and that Short Code context matters more than perfect gold SQL for downstream backtesting accuracy. A separate ablation showed **BM25 retrieval** in the Summarizer dramatically improves indicator identification (e.g., DeepSeek V3.2 accuracy rose from 17.65% to 68.98%).

10. **Limitations.** The authors note the dataset focuses on short-term daily-price timing strategies and excludes long-term/value strategies requiring multi-modal inputs (macro data, filings, news text); it targets feasibility/code-correctness verification rather than generating live alpha-producing advice; it uses simplified daily mark-to-market execution (buy at open/sell at close) without slippage or intraday microstructure; and it does not model dynamic fees, taxes, portfolio optimization, or ML/RL-based and ensemble meta-strategies, due to the combinatorial cost of extending the grid.

## 3. Key Importance Topics

### Large-scale benchmark construction for a vertical financial domain
BacktestBench is built from 6.5M+ real market records and 18,246 rigorously filtered QA pairs spanning four task categories (metrics calculation, ticker selection, parameter confirmation, strategy selection) that mirror the actual decision hierarchy of quantitative research.

**Why it matters:** Prior benchmarks (Text-to-SQL datasets, RL trading environments, small-scale coding benchmarks like QuantEval with only 60 problems) do not capture the temporal, look-ahead-bias-sensitive, multi-step reasoning unique to backtesting. A large, standardized, verifiable benchmark enables reproducible comparison of LLM capability in this domain and exposes failure modes invisible in generic coding benchmarks.

### Code-to-text reverse engineering with multi-model peer review
Natural-language strategy descriptions are generated from executable Python code (not the reverse), using five LLMs in parallel with docstring-guided context, then filtered by requiring unanimous approval from four other models across code fidelity and strategy validity dimensions.

**Why it matters:** This produces ground-truth-aligned, hallucination-resistant natural language annotations at scale (825,075 LLM calls) without expensive human authoring for every sample, while human audits (97.5%/98.5% pass rates) and an expert-crafted 70-strategy holdout set validate that the synthetic pipeline's difficulty structure matches real-world strategies.

### AutoBacktest's three-agent decomposition (Summarizer, Retriever, Coder)
Splitting the end-to-end task into semantic indicator extraction, validated SQL generation, and Python code execution — each with self-verification (BM25 matching, execution-based SQL validation, iterative code debugging) — mirrors how a human quant researcher actually works.

**Why it matters:** The paper shows decomposition plus grounding (BM25 retrieval, Short Codes) substantially outperforms letting an LLM do everything end-to-end from raw natural language, establishing a template for building reliable agentic pipelines in domains with strict correctness requirements.

### Short Code representation as a semantic anchor
Short Codes are compact, deterministic formula representations (e.g., `SMA(CLOSE,5)`) injected alongside full indicator names into Retriever/Coder prompts.

**Why it matters:** Ablations show Short Codes drive far larger backtesting accuracy gains than optimizing SQL quality alone — even models given perfect gold SQL but no Short Code context underperform those with imperfect SQL but good Short Code context — indicating that standardized, unambiguous intermediate representations are more valuable than end-task supervision alone for grounding LLMs in domain-specific computation.

### Decoupling of code executability from logical correctness
Non-CoT models like Kimi Linear 48B (99.22% ECR but 0.19% MC accuracy) and Seed OSS 36B (87.96% EA but 11.34% OA) generate syntactically valid, runnable code that is nonetheless logically wrong.

**Why it matters:** This demonstrates that execution success rate is a dangerously misleading proxy for correctness in financial code generation, and that Chain-of-Thought reasoning is necessary (not just code-generation fluency) to get genuinely correct quantitative results — a caution for anyone benchmarking or deploying LLM-generated financial code using execution-only metrics.

### Complex statistical KPIs as the dominant failure mode
Across all models, Volatility and Sharpe Ratio calculations are consistently the worst-performing metrics, driven by errors like missing "Day 0" capital anchoring, misapplied Mean Absolute Deviation, and improper annualization.

**Why it matters:** This pinpoints exactly where LLM-based financial code generation breaks down (statistical/distributional reasoning) versus where it succeeds (extreme-value tracking like Maximum Drawdown), giving concrete, actionable targets for future model or tooling improvements in quant-focused LLM applications.

## 4. Ideas for Development

- **Short Code-style deterministic aliasing for other domains** — Take the paper's Short Code mechanism (mapping natural-language indicator names to unambiguous formula strings injected into prompts) and apply it to any domain where LLMs must translate vague natural language into precise, deterministic computation (e.g., accounting formulas, engineering unit conversions, legal clause templates) to reduce hallucination and improve grounding.

- **Three-stage agent decomposition (Summarizer/Retriever/Coder) as a general agentic pattern** — Reuse the semantic-extraction → validated-retrieval → execution-with-self-correction pipeline structure for other "natural language to executable pipeline" problems, such as data analytics report generation, ETL job authoring from business requirements, or scientific computation from research questions.

- **Double-blind cross-validation for benchmark ground truth** — Apply the paper's practice of having two independent engineers implement the same computation and requiring exact match across randomly sampled test cases before accepting an evaluation harness, to any benchmark construction effort where correctness of the scoring function itself is a risk (not just the model outputs).

- **Peer-review filtering with unanimous multi-model consensus** — Use the paper's "one generator, four auditors, unanimous approval required" filtering scheme as a low-cost, scalable quality-control mechanism for any LLM-generated synthetic dataset (not just finance), particularly where hallucination or subtle logic mismatches are a concern.

- **Execution-accuracy vs. syntactic-executability as separate reported metrics** — Adopt the paper's practice of reporting Execution Correctness Rate (does it run) separately from Execution Accuracy/task accuracy (is it correct) whenever benchmarking LLM code generation, to avoid the "decoupling" pitfall where executable-but-wrong code inflates apparent capability.

- **KPI-difficulty-tiered evaluation for quant-focused LLM tools** — Build diagnostic test suites that separate "extreme-value" logic (e.g., max drawdown) from "distributional/statistical" logic (e.g., volatility, Sharpe ratio) when evaluating or fine-tuning any LLM-based quantitative research assistant, since the paper shows this is where model capability sharply diverges.
